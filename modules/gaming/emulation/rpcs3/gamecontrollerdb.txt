# SDL gamepad mappings.
#
# The entry below writes out exactly what SDL works out on its own for the
# JoyMouse pad, so it changes nothing about how the pad behaves. The file is
# here because RPCS3 looks for it and logs a warning when it is missing, and a
# mapping that agrees with the guess is the quiet way to answer that.
#
# The four face buttons look crossed further down the stack and are not.
# JoyMouse sends the TOP button as BTN_WEST and the LEFT one as BTN_NORTH,
# because the kernel header carries BTN_X as a second name for BTN_NORTH and
# BTN_Y as a second name for BTN_WEST, while SDL reads those header names and
# means its own x as the LEFT button and its own y as the TOP one. JoyMouse
# crosses the two codes so that the two crossings cancel. See linux/pad.rs in
# the joymouse sources for the long version.
#
# What is left is plain. SDL takes the face buttons in key code order, b2 is
# BTN_NORTH and becomes x, b3 is BTN_WEST and becomes y, north sits on top, and
# triangle arrives as triangle.
#
# The GUID is the bus, vendor and product the virtual pad announces, 0x1234 and
# 0x5678, so it only ever matches JoyMouse and no real hardware.
